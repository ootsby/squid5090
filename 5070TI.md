# squid5090 on an RTX 5070 Ti (16 GB): analysis, 2026-11-24

Nothing here has run the model yet. "Measured" = on this PC; "estimate" = scaled from upstream's 5090 numbers.

## Hardware
| | 5090 (upstream) | this PC |
|---|---|---|
| SMs / L2 | 170 / 96 MiB | 70 / 48 MiB (measured) |
| Read bandwidth | 1,513 GB/s | 873-879 GB/s median, random data (measured) |
| VRAM | 32 GB | 15.89 GiB reported, shared with the Windows desktop |
| Pinned host -> GPU | not published | 28.4 GB/s (measured, PCIe 4 x16, native Windows) |

Ratios: 0.58x bandwidth, 0.41x SMs. Same `sm_120a`, so the kernel instructions carry over.
All 5 CUDA files produced objects with no warnings, unmodified, with Windows nvcc 13.4 + MSVC (compiled only, not run).

## Fit (`python tools/vram_budget.py`; reproduces upstream's published sizes)
Only `nvfp4` can stay fully resident: `exact` 18.28 and `fp8` 16.85 GiB of weights (15.98 with host embed).
`--mode nvfp4 --kv q4 --embed-host`: weights 13.70 GiB; arenas 14.74 GiB at 8K, 14.96 at 32K. CUDA context is extra (unmeasured).
Desktop apps used roughly 1.8 GiB, ComfyUI about 11 GiB, when checked.

## Changes, in order
1. Build in WSL2 Ubuntu: CUDA 13.1+ and Zig 0.17.1+ (neither installed there). The Zig host is POSIX-only.
2. Pass `--embed-host` (existing flag): -0.86 GiB VRAM.
3. `prefill_batch_max` 2048 -> 512 in `src/engine.zig`: -0.51 GiB. Costs prefill speed. Audit `cuda/kernels_prefill.cu` first.
4. Chunk the 0.86 GiB load staging buffer in `weights.zig`. Load peaks at 14.56 GiB, above the 14.23 GiB needed to run at 8K after (3).
5. If still too big: expert banks of layers visited once and stored as NVFP4 (0-5, 18-19) in zero-copy host RAM,
   -0.53 GiB each. Estimate +1.3 ms per B=1 token, ~+6 ms per B=8 verify. Never layers 6-17: they run 3x.
6. Retune grids hard-coded for 170 SMs: `LM_HEAD_BLOCKS` 680, `DSPARK_UNEMBED_BLOCKS` 680, `MARKOV_BLOCKS` 340, `KV_SPLIT_K` 64.
   Larger than needed, not wrong. Profile before changing.
7. Generate `draft_vocab_32k.bin` (not in the repo): upstream says it halves draft time.
8. Re-measure with `bench` and `kld`. Upstream nvfp4/q4 KLD is 0.026. An `exact` reference will not fit here.

## Estimates (0.41-0.58x of upstream nvfp4, no expert offload)
Code 547-590 -> 225-345 tok/s; chat 316-333 -> 130-195; no speculation 249-263 -> 100-155; 20K prefill 8,755 -> about 3,600 at B=2048, less at 512.
Windows/WSL overhead and memory paging could push these lower.

## Update: measured VRAM limit (supersedes the desktop/offload assumptions above)
With ComfyUI closed, native Windows, idle desktop: 14.75 GiB of device allocations read at 869 GB/s with no paging (test capped there).
Windows evicted desktop VRAM to make room (nvidia-smi used: 2335 MiB before, 649 MiB after). Short test, small program; not yet repeated in WSL
or with the desktop in use. So `nvfp4` at 32K with prefill batch 512 (14.45 GiB) should fit without expert offload (step 5);
batch 2048 at 8K (14.74) is at the edge. nvidia-smi "free" (13.3 GiB) understates what a CUDA process can get.
